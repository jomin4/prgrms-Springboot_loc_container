# 1강 (v1) — IoC 컨테이너 기초: 하드코딩으로 빈 만들기

> 목표: 빈을 **하드코딩**으로 생성하고, 싱글톤으로 관리하며, 의존성을 생성자로 주입한다.
> 통과할 테스트: `ApplicationContextTest` t1~t6
> 규칙: `src/test` 수정 금지, 동적 클래스 로딩 금지, 하드코딩 허용.

## 이 강의 무대 — 3개의 빈과 의존 관계

- `TestPostRepository` — 의존성 없음 (가장 단순)
- `TestPostService` — Repository 주입 필요
- `TestFacadePostService` — Service + Repository 둘 다 주입 필요

핵심 규칙: **싱글톤** — 같은 이름으로 몇 번 불러도 항상 같은 하나의 객체를 돌려준다.

## 사이클 1 — 싱글톤 창고 + 가장 단순한 빈 (t4)

### 🧠 머릿속 그림
`ApplicationContext`를 **이름표 붙은 선반이 있는 창고**로 상상한다.
`genBean("이름")`을 부르면:
1. 창고(`Map<String,Object> beans`)에 그 이름의 물건이 **있나?** 확인
2. **있으면** → 그 물건을 그대로 꺼내 준다 (그래서 항상 같은 객체 = 싱글톤)
3. **없으면** → `new`로 만들어 → 선반에 올려두고(`beans.put`) → 준다

두 번째 호출부터는 항상 1번에서 걸리므로 새로 만들지 않는다.

### 코드 (com.ll.ioc.ApplicationContext)
```java
package com.ll.ioc;

import com.ll.domain.testPost.testPost.repository.TestPostRepository;

import java.util.HashMap;
import java.util.Map;

public class ApplicationContext {
    private final Map<String, Object> beans = new HashMap<>();

    public ApplicationContext() {
    }

    public <T> T genBean(String beanName) {
        if (beans.containsKey(beanName)) {          // 1) 있으면 재사용 (싱글톤)
            return (T) beans.get(beanName);
        }
        Object bean = switch (beanName) {           // 2) 없으면 하드코딩으로 생성
            case "testPostRepository" -> new TestPostRepository();
            default -> null;
        };
        beans.put(beanName, bean);                  // 3) 창고에 저장 후 반환
        return (T) bean;
    }
}
```

### 핵심 포인트
- `Map<String,Object> beans` = 싱글톤 레지스트리(창고). 온갖 타입의 빈을 담으려 값 타입이 `Object`.
- `containsKey` 검사 = 싱글톤의 심장. t3(`isSameAs`) 통과의 근거.
- `switch(beanName)` = 1강은 리플렉션 없이 하드코딩. (2강에서 이 부분을 리플렉션으로 제거)
- `(T)` 캐스팅 = 제네릭 메서드라 호출부가 원하는 타입으로 받음. 경고는 1강에서 무시.

### 검증
```
./gradlew test --tests "com.ll.framework.ioc.ApplicationContextTest.t4"
```

### 🔍 디버깅 정리 — genBean("testPostRepository") 2회 호출 실제 추적
| 단계 | 1번째 호출 | 2번째 호출 |
|---|---|---|
| 매개변수 `beanName` | `"testPostRepository"` | `"testPostRepository"` (동일) |
| `beans.containsKey` | `false` (비어있음) | `true` (1번째에서 put 했으니) |
| 처리 | `new` 생성 → `@18b4aac2` → `put`(크기 0→1) | `beans.get` → `@18b4aac2` 그대로 반환 |
| `new`/`switch` 실행? | O | X (if에서 바로 return) |

결과: `r1 == r2` → **`true`** (둘 다 `@18b4aac2`, 같은 객체). t3 `isSameAs` 통과 근거.
핵심: 싱글톤을 만드는 건 **`beans.put` 한 줄**. 이걸 빼면 매번 new → 다른 주소 → t3 실패.

## 사이클 2 — 의존성 주입(DI) (t2, t5)

### 🧠 머릿속 그림
`TestPostService`는 `TestPostRepository` 없이 못 만든다(생성자가 요구).
"빈을 만들려면 **재료(의존성)부터 `genBean`으로 조달**한다"가 핵심.
`genBean("testPostService")` → 창고 없음 → **재귀로 `genBean("testPostRepository")`** 호출해 싱글톤 조달 → `new TestPostService(repo)` → 저장·반환.

### 코드 (switch에 한 줄 추가 + import)
```java
import com.ll.domain.testPost.testPost.service.TestPostService;
// ...
case "testPostService" -> new TestPostService(genBean("testPostRepository"));
```

### 핵심 포인트
- 의존성을 `new`로 직접 만들지 않고 **`genBean(...)`으로 요청** → 이것이 DI의 본질.
- 인자 `genBean("testPostRepository")`가 **먼저 평가**되어 재료가 Service보다 먼저 생성됨.
- 반드시 `genBean`을 거쳐야 창고의 싱글톤이 공유됨. `new TestPostRepository()` 직접 넣으면 싱글톤 깨져 t5 실패.

### 🔍 디버깅 정리 — genBean("testPostService") 실행 순서
1. `genBean("testPostService")` → 창고 없음
2. switch 인자 `genBean("testPostRepository")` 먼저 실행(재귀) → repo `@764c12b6` 생성·저장(크기 1)
3. `new TestPostService(@764c12b6)` → service `@659e0bfd` 생성·저장(크기 2)
4. 나중에 `genBean("testPostRepository")` 직접 → 창고에 있음 → `@764c12b6` 재사용

증거: `service.repo(@764c12b6) == genBean(repo)(@764c12b6)` → **true** → t5 통과.
전 프로젝트에 Repository는 단 하나만 존재.

*(상태: ✅ 완료 — t2·t3·t5 통과 확인)*

## 사이클 3 — 의존성 2개 주입 (t6) · 1강 완성

### 🧠 머릿속 그림
`TestFacadePostService`는 Service + Repository 둘 다 주입받음.
생성자 순서 = 필드 선언 순서 = `(TestPostService, TestPostRepository)`.
사이클2와 원리 동일("재료부터 조달"), 재료가 2개일 뿐. genBean 재귀가 연쇄됨.

### 코드 (switch에 한 줄 + import)
```java
import com.ll.domain.testPost.testPost.service.TestFacadePostService;
// ...
case "testFacadePostService" ->
        new TestFacadePostService(genBean("testPostService"), genBean("testPostRepository"));
```
⚠️ 인자 순서(service, repo)가 생성자 파라미터 순서와 일치해야 함.

### 🔍 디버깅 정리 — 주입의 연쇄 (창고 크기로 추적)
1. `genBean("testFacadePostService")` → 없음
2. └ `genBean("testPostService")` → 없음
3.    └ `genBean("testPostRepository")` → 없음 → repo 생성·저장 (크기 0→1)
4. service 생성(repo 주입)·저장 (크기 1→2)
5. 재료2 `genBean("testPostRepository")` → **있음** → 재사용
6. facade 생성(service+repo 주입)·저장 (크기 2→3)

증거(t6): `facade.service == genBean(service)` → true, `facade.repo == genBean(repo)` → true.
게다가 `facade.repo`, `genBean(repo)`, `facade.service가 품은 repo` 세 곳 모두 같은 주소 = Repository는 단 하나.
※ `@주소`는 실행마다 달라짐(identityHashCode). 중요한 건 "서로 같은가"이지 값 자체가 아님.

*(상태: ✅ 완료 — t6 통과 확인)*

## 🎉 1강 완주 (t1~t6 전체 통과)

### 배운 것
- **IoC/DI**: 객체 생성·연결의 제어권을 컨테이너에 넘기고, 의존성을 생성자로 주입.
- **싱글톤**: `Map` 창고 + `containsKey` 검사로 빈을 한 번만 생성해 재사용.
- **재귀 조립**: `genBean`이 서로를 호출하며 의존성 그래프를 조립. 재료는 항상 `new`가 아닌 `genBean`으로 조달해 싱글톤 공유.

### 완성된 genBean 로직
```
1) 창고에 있으면 → 그대로 반환 (싱글톤)
2) 없으면 → switch로 하드코딩 생성 (재료는 genBean 재귀로 조달)
3) 창고에 저장 → 반환
```

### 1강의 한계 → 2강 예고
`switch(beanName)`는 빈이 늘 때마다 손으로 case를 추가해야 함(하드코딩).
2강에서 **리플렉션 + 컴포넌트 스캔**으로 이 switch를 통째로 제거 → 애노테이션만 붙이면 자동 등록되는 진짜 스프링 방식으로 진화.
